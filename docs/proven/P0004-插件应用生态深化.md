# 插件应用生态深化

- 状态：已完成（封存）
- 日期：2026-09-10（回溯归档；主体 2026-09-04 至 09-09 分波落地）
- 关联：PRD D06/D07/D15/D22/D23/D25/D32/D33/D35/D36/D37/D38；方法 R002；标准 G002；研究 S002/S003；踩坑 M102/M103；diary 全程

## 背景与问题

应用从移植件（web-fetch/搜索/x-monitor 全家桶）成长为自研生态，三重缺口：无统一开发标准（各应用形态各异）、无类型护栏（apps 是 .mjs 纯 JS）、语义层能力不足（整页 DOM 喂模型、站点知识不可达、无隔离引擎）。同时 x-intel 作为最重的常驻应用，稳定性问题（人机共存、锁竞争、收割风暴）持续暴露。

## 目标与非目标

目标：

1. 应用开发有标准有门禁（G002/R002），新应用照模子落地
2. apps 层类型护栏不改变分发模型（拷贝即用）
3. 语义层观测效率与资产可达性（元素引用、站点知识、技能分发）
4. 自起 headless 引擎：临时隔离、可克隆登录态、用完即杀，与附着模型并存
5. x-intel 收割稳定：限流、容错、文案如实

非目标：

- 不做 MCP 桥接；不做上游没有的新功能（D37 引擎为 D02 agent-Chrome 能力的引擎版回归，属平台补齐）
- apps 不改 .mjs 分发模型（不进编译链）

## 方案

- **标准族（D06/D07）**：通读 nu_plugin_browse skills 生态四仓提炼 R002（固定形合约/两步契约/会话生命周期/错误分类）+ G002（强制项/禁令/验收门禁/迁移分级）；google-search 首落地立样板（ensure_app_sdk 基建 + __gs 常驻 SDK + esbuild 构建链）
- **应用线**：medium-search（D15，CF 实测结论沉淀：冷 HTTP format=json 403、页内 fetch 连续请求挂起、DOM 水合瞬态摘除）、bing-search G002 化（D22，修 title 偶发空）、super-ocr（D25，ppu-paddle-ocr 装BH_HOME/ocr，核心包零 runtime 依赖）、web-fetch Defuddle 升级（D33）
- **类型护栏（D32）**：tsconfig.apps.json（allowJs + checkJs + noEmit，strict 减 noImplicitAny）纳管 assets/apps，npm test 前置；清 41 处真错误
- **版本化元素引用（D35，S002 吸收）**：snapshot_interactives 出最小观测面 `{version, items:[{ref,role,name,tag,box}]}`（a11y 风格，上限 50 + total 如实）；click_ref/fill_ref 按 ref 重解析 + elementFromPoint 自证，陈旧报 STALE_REF、畸形报 BAD_REF
- **技能资产激活（D36）**：分发面扩 primitives + domain-skills（94 站 1.6MB 进 ~/.claude 与 ~/.codex 技能树）；domain-skills 提示默认开；新原语 bh skill sites / skill site 段；SKILL 动手前硬性两步
- **自起 headless 引擎（D37，S003 正解）**：临时 user-data-dir + port 0 + DevToolsActivePort 发现 + BH_CDP_WS 钉死连接的专属 daemon；句柄落 runtime/engine.json 防孤儿；--cookies 从用户浏览器单向克隆登录态；命令定名 bh headless（别名 hl）；生命周期铁律：临时 profile、退出必杀、绝不碰用户 profile
- **x-intel 稳定线**：search/harvest 固定形合约（D23）；GitHub issues 双修（D26：tab 所有权马标记认领、后台 fill_input 回读）；D38 收割风暴限流接线（主循环触发后收割前置 60 秒闸，带心跳等待）；0.6.5 状态文案对齐（节奏值模板引用 MIN_ROUND_SPACING 常量防漂移）

## 备选方案

- apps 全 TS + 构建期产物分发：否决（D32 裁定），拷贝即用是分发根基，类型护栏换轨 checkJs
- Lightpanda 无头引擎适配：否决（S003），Windows 仅 WSL2 且无渲染引擎致 652 直调面不成立；自起 headless Chrome 是其超集方案
- x-intel 收割风暴修 title-badge 触发降权：未采纳为首选，先接限流闸（声明未接线的原设计意图），降权留观察
- 上游 js 仓 auth.json 修复等：以回流形式吸收（cookie-io 受控 JSON 解析），不整块同步

## 风险与回滚

- 风险：checkJs 动态形状收窄爆炸（渐进后置 noImplicitAny 化解）；Defuddle 构建链引入 devDependency 依赖面（esbuild 仅构建期）；引擎临时目录残留（句柄 + 退出必杀双保险）
- 回滚：Defuddle 失败降级原启发式不断供；引擎独立命令面可整体停用不影响附着模型

## 实施过程与经验

- **D38 根因模式（本篇最新经验）**：常量「声明未接线」类 bug 的检出信号是日志节奏与设计意图不符；诊断入口先数日志时间戳分布，再看该常量读写引用是否闭环。叠加触发探针 title-badge (N) 在后台 tab 永不清零，触发常燃
- **文案漂移教训（0.6.5）**：状态类硬编码字符串随行为演进静默漂移（「5 秒探测」为 D34 错峰前残留）；凡节奏/间隔/上限类展示值一律模板引用同源常量
- **资产存在不等于可达（D36 三要素）**：分发到位 + 默认触发 + 一条命令可读，缺一即僵尸资产
- **CDP 大返回冻结（D33 根因）**：整页 outerHTML（几 MB）回传触发冻结，medium「老是 500」即此；页内提取只回 KB 级正文是通用解，自家 M102 规违了自己
- **两步契约的价值（D07 起反复验证）**：指标落盘 + pluck 取数让「跑一次看结果」与「事后取指标」解耦，agent 工作流不依赖一次性 stdout
- x-core 合一再解耦（0.2.0 至 0.2.1）：合一应用初衷是省 IPC，解耦恢复独立生命周期的收益更大；supervisor 随后抽成 supervisor-core（D21），应用边界按「独立生命周期 + 独立卡片」划分
- SDK 是 TS 例外：页内注入需 esbuild 构建 IIFE，构建期 devDependency，运行时白名单不动
