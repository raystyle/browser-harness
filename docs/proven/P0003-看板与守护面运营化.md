# 看板与守护面运营化

- 状态：已完成（封存）
- 日期：2026-09-10（回溯归档；主体 2026-09-07 至 09-09 分波落地）
- 关联：PRD D12/D13/D16/D17/D18/D19/D20/D21/D29/D30/D31/D34；研究 S004；踩坑 M103；diary 2026-09-07 至 09-09

## 背景与问题

平台长出常驻面后（daemon 实例、rmux 会话、worker 进程、页面守护），运维全部黑盒：实例活着没有统一答案、应用挂在看板外无感知、墙拦截漏报、升级靠手工搬包停起、锁竞争不可见。需要一层只读运营面与一套滚动机制。

## 目标与非目标

目标：

1. 一屏可见：实例健康、附着面、rmux 会话树、worker 心跳、页面判定、事件尾
2. 需要人工介入时找得到人：墙类告警经看板弹 Chrome 系统通知
3. 升级轮换程序化：版本漂移自动检测、显式滚动、终验对版
4. 初始化幂等：首次使用自动带起 companions，不动既有附着

非目标：

- 看板不做写操作（只读铁律，永久）
- 不做自动发版（semantic-release 类，S004 裁定与 diary 治理链冲突）
- 不引入桌面 GUI

## 方案

- **只读看板（D12）**：127.0.0.1:9870，SSE 推送，macOS 风格三面（实例/附着面/rmux）+ worker 心跳与事件尾。只读铁律程序化：看板页不是工作 tab，default 与应用禁止 attachFirstPage/goto_url/switch_tab/new_tab 附着它
- **应用卡片区（D17）**：平台层自动记录（runPlugin 落 app-runs.jsonl + 捕获 stderr 尾行），应用导出 description 常量，应用零改造接入；折叠/拖拽态存 localStorage。统一状态合约（G002）：常驻应用发布 `{_v, ts, state, metrics[], event}` 单模板渲染
- **墙通知（D16）**：verdict 边沿触发 + requireInteraction + tag 去重 + 点击只聚焦看板；通知经已授权源展示
- **通用页面守护（D18）**：page-detect watch 常驻只读探测附着浏览器全部 http(s) 页面，10 秒 ±15% 抖动 + 页间 150ms；白屏持久化（2 周期）与资源被 CF 阻断（performance 时序 403/429/503）纳入自动告警
- **初始化原语（D19/D20）**：使用前判系统环境（Node 版本闸），ensureDaemon 成功/半活皆 fire-and-forget 带起看板、rmux 守护、page-detect watch、supervisor-core；幂等不动既有附着。x-intel 按需显式启动不自动
- **supervisor-core（D21）**：从 x-intel 内嵌 x-supervisor 抽成独立通用监督应用，统一守护 page-detect 与 x-intel worker（心跳超时重拉），有自己的应用卡
- **CLI 工程化（D29）**：commander（解析）+ zod（env/选项校验）入 runtime 白名单（零依赖承诺改白名单制）；写操作默认 dry-run、--yes 执行；统一退出码表（0/1/2/3）；全部命令界面保形
- **升级轮换（D30）**：任意 bh 命令启动比对 health.version + buildTime，漂移 stderr 提示一行；`bh upgrade` 默认 dry-run，--yes 六步滚动（x-intel 拆栈、companions 停、default 重生、named daemon 逐个重生、dashboard 换新、x-intel 恢复）；包源三态（Release 默认不降级 / --from 显式源后台引导安装规避 Windows 文件锁 / --offline 只滚动本地）；stopped 状态尊重不拉
- **单飞锁清算（D31）**：daemon 侧每 eval 清算上限（超时未结算过宽限期自动释放单飞槽）；page-detect watch 连续 2 次 eval busy 自动重启自身 daemon 兜底
- **只读旁路（D34）**：daemon 新增 GET /tabs 与 GET /peek 只读端点不占单飞锁；看板快照改旁路；remote 层 429 退避重试（400ms/1.2s 两级）；应用节奏错峰标准落 G002 第 8 条（互质 + 抖动 + 页间 gap）

## 备选方案

- 看板数据面走每实例 eval：初版即此，D34 证伪（每秒 6+ 次几乎常占单飞锁），改旁路端点
- semantic-release 自动发版：否决（S004），单人 trunk 直推 + Conventional Commits + R001 手动封版八步为合法形态
- 升级全停全起：否决，滚动序列保 x-intel 收割连续性；x-intel stopped 状态尊重不拉避免误启动

## 风险与回滚

- 风险：看板自身成为负载（D34 已证并修）；滚动中 Windows 文件锁（--from 后台引导安装规避）；supervisor 与被守护者互踢
- 回滚：看板可独立停（dashboard stop）；upgrade 失败卡中间态时各步幂等可重入

## 实施过程与经验

- **D34 真凶方法论（本篇最有价值经验）**：跨应用冲突先画「谁连谁的 daemon」拓扑（每 daemon 一把单飞锁，锁冲突必同 daemon），再数每客户端请求频率与持锁时长，占锁率一算真凶自明。表象「page-detect 与 x-intel 互撞」实为看板两头抢锁，且看板自己撞的 429 被 catch 静默
- **Commander 三连环**（D30 实机逐一抓出）：新命令必须注册 KNOWN_COMMANDS 否则被 legacy 裸片段路径吞；无参命令 action 第一参是 opts 对象非命令对象；顶层 flag 会抢占子命令同名 flag（enablePositionalOptions 解）。选项解析类改动必须逐命令带 flag 实测，dry-run 与 --yes 两条路径都走
- **滚动盲区**：companions 重拉只附着已活 named daemon 不换代码，upgradePlan 需显式重生步；终验改轮询（start 返回时 daemon 尚在附着，单发探测误报）
- **daemon 侧修复必须先滚动 daemon 再复验**（D31 教训：0.4.2 装了 CLI 没滚动，验证假失败）；人为挂锁（await new Promise 不结算 + 短超时）是单飞锁行为的可复现探针
- 看板渲染实例状态曾因前端读旧嵌套结构恒显 down（0.2.1 首修）：状态合约字段演进时消费端同步是薄弱点，后由 D17 统一模板收敛
